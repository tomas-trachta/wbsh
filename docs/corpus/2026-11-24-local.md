# Real-world corpus, 2026-11-24, local

**wbsh sourced 968 of 1,034 runs cleanly (93.6 %). Git Bash sourced 969 of
the same 1,034 (93.7 %) in the [2026-11-13 snapshot](2026-11-13-local.md),
with the same pins on the same machine.** The two parser bugs behind most of
that snapshot's wbsh failures (B12 and B28 in the
[ledger](../compat-ledger.md#shell-bugs-found)) are fixed. oh-my-bash,
bash-completion, nvm, sdkman, asdf and git's completion scripts now come out
the same as under Git Bash, and bash-it is one run short. Almost every
remaining failure is a plugin for a tool that is not installed (`chruby`,
`pg_config`, `fasd`, `jenv`, `powerline`, ...), which fails under Git Bash
too.

Produced with [`tools/corpus/run.py`](../../tools/corpus/README.md) and the
pinned [`manifest.json`](../../tools/corpus/manifest.json), wbsh only:

```sh
python -I tools/corpus/run.py --shell wbsh=x64/Release/wbsh.exe \
    --clone-root C:/scratch/corpus-src --low-priority --jobs 4 \
    --markdown snapshot.md --json corpus.json
```

- wbsh: 1.2.0 (`x64/Release/wbsh.exe` from 41bc226), plus the fix that makes an
  interactive shell keep an empty `PS1` inherited from the environment and
  honour `--noediting`. Without it every interactive run printed the default
  prompt to stderr, since 1.2.0 made `-i` on piped stdin interactive.
- Git Bash was not run again; its numbers are in the 2026-11-13 snapshot.
- Machine: Windows 10 22H2 (19045), Ryzen 7 5800H, 16 GB; 4 runs in
  parallel at below-normal priority.
- starship, zoxide, direnv and fzf were not installed on this machine, so
  their generated init scripts were skipped.
